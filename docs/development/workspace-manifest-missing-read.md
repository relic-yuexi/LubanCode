# Windows workspace manifest 缺档读合同

CI `36997253363` 在源 `b703cd6600e657679f30cdec6d12cbcd3aee0c58` 上跑出两次缺档读。
`integration.workspace.identity_cross_platform` 的 `bad_reads == 0` 断言失败。
两次都报 `Missing`，错误码与文本为空；没有破损 JSON。

读口用 `fs::exists` 探测。它返回 `false` 且没有错误时，旧实现立即报 `Missing`，绕过已有读重试。
这份原件只能证明并发替换时观察到缺失。它没有留下那两次系统调用的原始错误或文件快照，不能据此断言 `MoveFileExW`、过滤驱动或别的机制就是根因。

本批只改 Windows 的缺档读：把这类缺失放进原有读循环，复用最多十次退避，每次 10ms，总退避预算仍为 100ms，最多探测十一回。
不另套循环，不延长已有探测／打开重试。预算只限制重试与退避，不替阻塞文件系统调用承诺硬期限。

最后一轮仍查无文件，就返回 `Missing`，错误码与文本仍为空。存在但打开或探测失败，仍留原有诊断。
读到坏 JSON，立即返回 `Corrupt`，绝不靠重读改判。POSIX 缺档仍立即返回。
Windows 首次开空仓也会走这段重试，计划退避最多 100ms；写口、原子写回执、SDK、Worker 与 Runner 协议都沿旧合同。

验收保留原并发册八手各写四十次、读侧十次各等 2ms、`bad_reads == 0` 及末态校验，半条不减。
另补真缺档的终态与空诊断、缺档后延迟发布的恢复、坏 JSON 的拒绝。
延迟发布册预写完整临时档，再留出真实缺档窗口，最后经生产同源换名口发布。线程信号在首次探测前发出，只标线程启动；这不是观察首次缺档的白盒闸，也不单独证明原失败的系统调用根因。
三平台在远端 CI 实跑。指定读口两册还须保存登记、JUnit 与完整原生输出，确认新册非零；全量 CI 任一红灯都不验收。

源 `8478a66a` 的 CI `37007955052` 在 Linux 指定门跑过两册原生（12／99、4／21）及七项纯数据检查，随后 Git 头校准返回 128。旧脚本捕获 stderr 却没有输出或保存，原件不足以单独确定 Git 拒绝原因；这轮仍报失败，全量与启动检查按前置门跳过。
后续只修 CI 校准口：从脚本定位真实仓库目录，定向传 `git -c safe.directory=<真实仓库> rev-parse HEAD`，不改全局 Git 配置，也不放宽与 `GITHUB_SHA` 的精确比较。Git 失败须先存原 stderr，再打印；控制台编码失败也不能盖掉原 Git 异常或错头拒绝。补错头、Git 失败、stderr 编码失败三类纯数据反例，原生源码、注册与计数都不动。
